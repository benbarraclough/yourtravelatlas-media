No music. Public copy is inspiring and concise. Not a claim of guaranteed 100% posting uptime; no external source/licence/API can be guaranteed.

## Governing success condition
A successful *publishing* run results in **Metricool-confirmed PENDING** with exact media/count/order, full reviewed text, correct future time, autoPublish=true, draft=false, no duplication and within verified allowance. A research brief, render, task 'completed' or QA note never counts as a scheduled post. In the day-of-publication audit, reconcile `PUBLISHED` or `FAILED_PUBLICATION`. Maintain a 14-day scheduled lead where actual quality and capacity allow. A missed 7-day slot or zero pending posts is a **red operational failure**, not 'no action needed'.

## Cross-run state machine
`IDEA -> COMMISSIONED -> IN_PROGRESS -> RENDERED_PENDING_QA -> QA_APPROVED -> SCHEDULED -> PUBLISHED`.
For a QA failure, `RENDERED_PENDING_QA -> REVISE -> IN_PROGRESS -> RENDERED_PENDING_QA`; if fundamental rights, accuracy or quality barriers are not fixable, `REJECTED` and **commission/produce an entirely new replacement, linked to the rejected original**. For a rendering failure `IN_PROGRESS -> REVISE` with exact failing test, image, licensing issue or unavailable URL, then correct and rebuild. For a provider failure `QA_APPROVED -> SCHEDULING_ERROR`, inspect and retry with idempotency checks. For publication failure `SCHEDULED -> FAILED_PUBLICATION`, inspect provider reason and remediate rather than silently moving on. For a published or scheduled edition, never rerun production simply because a stale queue entry says pending QA. **Live Metricool is authoritative for actual scheduling and publication; GitHub records need correcting on every check.**

## Exact mandatory feedback handoff (GitHub, not model memory)
After EVERY QA reject/revise or render/import error, write a machine-readable entry in `content/quality-feedback.json` and detailed review evidence under `content/reviews/`. Include unique edition ID, source brief SHA-256, rendered output SHA-256s when present, failed gate, reason code, explicit error text/observed visual mismatch, file/slides affected, remedy or pivot criteria, replacement concept if pivoting, responsible next stage, attempt number, status and date. `content/production-queue.json` must point to the feedback ID and actionable next step, with a revision chain (`parent_edition_id`, `replacement_edition_id`, `revision_count`). Do not maintain independent contradictory status fields. Re-fetch SHA before writes, merge competing edits, never overwrite another task's changes.

Required failure codes: `WRONG_SUBJECT`, `WEAK_MEDIA`, `COPY_IMAGE_MISMATCH`, `FACT_UNVERIFIED`, `RIGHTS_UNVERIFIED`, `MISSING_SOURCE`, `RENDER_FAILURE`, `HASH_STALE`, `MOBILE_READABILITY`, `METRICOOL_ERROR`, `EMPTY_SCHEDULE`, `OTHER`. A failure without an actionable remedy is not a finished review.

## Bounded recovery loop, persistent across runs
1. **Reconcile first:** fetch live provider dates/status, latest queue + feedback. Correct any mismatch before choosing an edition; reserve only real unoccupied publishing slots.
2. **Repair rather than restart:** if QA names one or two fixable defects (bad wording, misleading image, bad crop/format, licensing missing source), repair that exact brief/media, rebuild, compare new SHA and re-QA **within the same execution when possible**. Never reuse old QA PASS for changed copy or image. Attempt up to two substantive corrections to an edition before pivot unless clear material progress justifies one more.
3. **Replace rather than stall:** if a required asset cannot be found, cannot be licensed, or fails visually, switch in the same production run to a sourceable alternate concept. A substitute may retain the list premise while changing an item **only if the published headline and new complete list remain truthful**; log rejected and replacement subjects. No fake AI images, invented tags, made-up permissions or weak filler.
4. **Continue after rejection:** queue the next eligible replacement, carry explicit `retry_on_next_run=true` and `handoff_to` values. Every next production/recovery run checks unresolved feedback **ahead of new commissions** and continues the highest-priority defect or replacement until a complete pass or a true externally unavoidable blocker. Do not allow any rejected idea to occupy all runs. Stop/restart around task execution limits while saving durable evidence; never claim infinite retries during one single run.
5. **QA feedback is a test case:** every defect gets a reusable prevention lesson (e.g. subject/verb mismatch between overlay and actual pixels; renderer missing required `activity_source`; unsourced licence strings; failing preview-to-caption relevance). Preflight future briefs against lessons; add deterministic automated test when technically possible, keep semantic/visual gates as actual human-like image inspection.
6. **Publish/check/learn:** if QA PASSES, schedule at the earliest genuinely eligible spaced vacancy, re-fetch from Metricool, update `CURRENT_STATE.json` and ledger immediately. If not pending, don't count it. After publication compare provider status, record which revisions improved validity, and share small proven process fixes with all automations. Never infer engagement gains without analytics.

## Buffer and watchdog
- At the **start and end of every scheduled operation**, compute current pending count and earliest 7-day/14-day publishing gaps from live Metricool, not planned queue. Target Mon 19 / Wed 12 / Fri 19 / Sun 17 UK, adjusting genuine dates/times; within 20 monthly cap and any stricter plan.
- When there are **fewer than two genuinely scheduled posts in the next seven days, or an upcoming normal publishing slot is empty**, enter RECOVERY_PRIORITY. Production and QA override elective research/status commentary in favour of exact delivered media and scheduling. Existing blocked item receives one focused fix effort, then pivot to a more tractable concept; a new excellent post still needs all seven quality gates.
- The daily evening recovery job is the **safety net**: repair mis-synced states, attempt the nearest eligible handoff, source replacement and schedule only if truly PASS, never duplicate. If still empty, leave an explicit actionable failure report with an owner-visible notification. Escalate persistent genuine tool/rights blockers; no routine approvals required.
- Maintain a **backlog of at least four conceptually strong, source-feasible candidates**, representing a range of formats/regions. Do not count an idea as rendered. Reject nonfeasible commissions up front. At least one fallback must be sourceable without paid media. If no sourceable fallback exists, commission one promptly rather than rerunning the exact failure indefinitely.
- Tasks report `researched / rendered / QA_PASS / scheduled / published / upcoming pending count / earliest gap / feedback records changed / blocking reason`. End every run with concise nonempty owner-visible status. Do not report success when `scheduled=0` and open slots remain.

## Roles and process coordination
- Research supplies ranked, licensed-photo/clip feasible ideas and backups, reads `quality-feedback.json` for recurring failures, rejects hard-to-license concepts earlier.
- Production owns concrete source replacement, corrected brief, test/rerender and evidence. Must inspect its actual output; cannot self-approve for scheduling.
- Review challenges every final image in full and phone-size, real motion for reels, all seven gates; writes exact pass/revise records; after PASS schedules and verifies. On REVISE gives precise edits that production can execute without guessing; if able, invokes correction during the same run; never mistakes 'not produced' for 'quality passed'.
- Recovery operates even when upstream jobs say complete. It reconciles provider to ledger, drives pending work forward, can commission/produce/review a fallback where genuinely possible, and alerts on gaps.
- Growth evaluates actual rejection categories and publish performance monthly, proposes small specific process improvements; does not replace all-seven-gate editorial QA with engagement pressure.
